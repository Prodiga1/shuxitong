# 数析通 任务规划

## 1. 规划依据

任务拆解依据 [设计文档](design.md) 第 9 节的十二项已定决策。

| # | 已定决策 | 对任务规划的影响 |
|---|---|---|
| 1 | Planner 受约束规划，拓扑由模板决定 | M2 增加 skill 模板库，模型只能选模板并填槽 |
| 2 | SQL 语义层编译为主，模型直出为逃生舱 | M3 拆成"编译器主路径"与"模型逃生舱"两条链路 |
| 3 | 记忆混合检索（BM25 + 向量 + RRF） | M4 增加向量索引、融合排序与反馈闭环 |
| 4 | Spark 可切换，诊断用 local-cluster | M0 会话工厂支持多 master；M6 不再需要真实集群 |
| 5 | 语义层手写为主、反射为辅，CI 查漂移 | M3 增加反射草稿与漂移检测 |
| 6 | 核心为库，CLI 与 HTTP 是适配器，job 异步 | M1 的 job 模型从设计上就是异步的 |
| 7 | 不做界面，产物必须结构化 | M1 固定每个 skill 的输出 schema |
| 8 | 图产物为血缘图与依赖图，对齐 OpenLineage | M7 按 OpenLineage 事件模型实现 |
| 9 | 合成数据作为一等测试夹具 | M0 增加数据生成器，M6 的演练数据由它产生 |
| 10 | 语义层按主题域分文件，版本用内容哈希 | M3 的加载器要支持多文件合并与哈希计算 |
| 11 | 指标结构化表达 | M3 的编译器按字段拼接而非解析整条表达式 |
| 12 | 模型服务走 DeepSeek，经 ModelClient 抽象 | M0 增加模型客户端，M2/M3 依赖它 |

## 2. 里程碑总览

| 阶段 | 主题 | 关键交付 | 依赖 |
|---|---|---|---|
| M0 | 基建 | 环境自检通过，合成数据与模型客户端可用 | — |
| M1 | 状态与模型 | job / step / attempt 可落库并流转 | M0 |
| M2 | 编排器 | 受约束规划与重试机制可被测试验证 | M1 |
| M3 | 问数闭环 | 只读安全问数端到端 | M1 |
| M4 | SQL 记忆 | 混合检索召回可用 | M3 |
| M5 | ETL 与多步 | 多步 DAG + 数据质量报告 | M2 |
| M6 | 作业诊断 | EventLog 结构化诊断报告 | M2, M5 |
| M7 | 归档与可观测 | CLI 全流程查询 + 血缘图 | M3–M6 |

M1 之后路线分叉：**问数线**（M3 → M4）和**编排线**（M2 → M5 → M6）可以并行推进。关键路径是 M0 → M1 → M2 → M5 → M6。

## 3. M0 基建

| 编号 | 任务 | 交付物 | 验收要点 |
|---|---|---|---|
| T0.1 | 项目骨架与依赖管理 | `pyproject.toml`、`src/shuxitong/` 库布局、`uv` 锁定依赖 | `uv run python -c "import shuxitong"` 通过 |
| T0.2 | 配置系统 | 设置模型（路径、Spark 参数、模型参数）、`.env.example` | 缺失必填项时报错清晰，密钥不落库不进日志 |
| T0.3 | SparkSession 工厂 | 统一会话创建与关闭，支持 `local[*]` / `local-cluster` / standalone 三种 master | 三种模式各跑通一条 `SELECT 1`，eventLog 开关可用 |
| T0.4 | Docker 环境 | Dockerfile、compose、卷定义 | 容器内跑通 T0.3 的同一条查询 |
| T0.5 | 日志与异常体系 | 结构化日志、`RetryableError` / `BusinessError` 基类 | 异常层级单测 |
| T0.6 | 环境自检命令 | `shuxitong doctor` | 打印 Java / Python / Spark / SQLite / Docker 版本与可用性 |
| T0.7 | 合成数据生成器 | 电商星型模型生成脚本，支持参数化注入倾斜、spill、join 放大 | 生成的 Parquet 可被 Spark 读取，病态现象可复现 |
| T0.8 | ModelClient 与 DeepSeek 接入 | 基于 `openai` SDK 的客户端抽象 + DeepSeek 实现 | 一次调用成功；模型名与 token 用量可记录 |

两条说明。`local-cluster[2,1,1024]` 是 T0.3 的硬性要求，不是可选项——诊断模块的演练数据依赖它产生多 executor 的 EventLog。T0.7 的"参数化注入"也是硬性要求，固定数据只能验证正常路径，验证不了诊断规则。

`.env` 已在 `.gitignore` 中排除，新增 `.env.example` 登记 `DEEPSEEK_API_KEY` 等占位符。密钥只从环境读取，不落库、不进日志、不进镜像层。

## 4. M1 状态与模型

| 编号 | 任务 | 交付物 | 验收要点 |
|---|---|---|---|
| T1.1 | 核心数据模型 | Pydantic 模型：Request、Plan、Step、Dependency、SkillSpec、Attempt、Artifact | 模型能表达嵌套依赖，非法参数被拒 |
| T1.2 | 产物输出契约 | 每个 skill 的输入输出 JSON schema | 产物可被机器消费，无纯文本日志输出 |
| T1.3 | SQLite schema 与迁移 | 建表脚本 + 版本化迁移 | 空库能一键初始化，重复执行幂等 |
| T1.4 | 存储层 | repository 封装，单写者串行化，事务边界明确 | 并发写测试不丢记录 |
| T1.5 | 异步 job 模型 | 提交返回 `job_id`，状态查询与执行解耦 | 长任务不阻塞调用方 |
| T1.6 | 状态机 | Job / Step / Attempt 的合法流转规则 | 非法流转（如 SUCCEEDED → RUNNING）被拒绝 |
| T1.7 | Skill 注册表 | 固定工具集声明：名称、参数 schema、输出 schema | 未注册的 skill 无法进 Plan |

T1.2 与 T1.5 是决策 6、7 的直接落地。产物契约如果拖到后面补，M3 之后的所有 skill 都要返工。

## 5. M2 编排器

| 编号 | 任务 | 交付物 | 验收要点 |
|---|---|---|---|
| T2.1 | 依赖图与拓扑排序 | DAG 构建、环检测、拓扑序 | 有环的 Plan 在提交时就被拒 |
| T2.2 | Skill 模板库 | 每个 skill 的 Plan 模板与参数 schema | 模型只能从模板集中选择并填槽 |
| T2.3 | Step 执行器 | 按拓扑序推进，逐步落 step / attempt | 中途中断后可看出停在哪一步 |
| T2.4 | 重试策略 | 指数退避、上限、仅限可重试错误 | 业务失败不触发重试 |
| T2.5 | 错误分类器 | 异常类型 + 错误码 + 消息模式 → `retryable` / `business` | 一组样例异常分类结果稳定 |
| T2.6 | 产物管理器 | `artifacts/{task_id}/{step}/{attempt}/` 归档、sha256、manifest | 重跑不覆盖历史 attempt |

T2.2 是决策 1 的落地。模板库承担两个职责：限制模型的输出空间，以及给校验闸门提供"这个 skill 的合法参数长什么样"的权威定义。

M2 用一个**故意可配失败的假 skill** 做验收：同一次测试里验证「可重试的重试后成功」「业务失败立即终止」「下游标记 SKIPPED」「历史产物保留」四件事。

## 6. M3 问数闭环

| 编号 | 任务 | 交付物 | 验收要点 |
|---|---|---|---|
| T3.1 | 语义层定义与加载 | 按主题域分文件的 YAML 格式、多文件合并加载、内容哈希版本 | 版本变更能被历史记录区分，改任一文件哈希即变 |
| T3.2 | schema 反射草稿 | 从数据源反射表、列、类型、主键、行数、样例值 | 草稿可合并进 YAML，不覆盖人工内容 |
| T3.3 | 漂移检测 | 物理 schema 与语义层比对 | schema 变更触发 CI 报警 |
| T3.4 | 语义层解析与归一 | 把自然语言里的实体、指标、维度归一到受控词表 | 无法归一时明确报错而非瞎猜 |
| T3.5 | 语义层 SQL 编译器 | 结构化指标 + 维度 + 过滤条件 → SQL，确定性生成 | 同一输入产出同一 SQL；非法聚合或不存在字段在编译前被拒 |
| T3.6 | SQL 校验闸门 L1–L4 | 基于 AST 的单语句、语句类型白名单、对象白名单、危险构造拦截 | 越界用例集全部被拒 |
| T3.7 | 执行边界 L5–L6 | 只读视图注册、强制 LIMIT、查询超时、返回字节上限 | 超限查询被截断或拒绝 |
| T3.8 | 模型生成逃生舱 | 语义层覆盖不了时由模型直出 SQL | 与主路径共用同一套校验与执行边界 |
| T3.9 | ask skill 端到端 | 问数全流程 + 审计记录落库 | 一条问数留下完整决策链 |

T3.5 与 T3.8 是决策 2 的落地。两者的关系要写死：**逃生舱不是绕过校验的通道，它和主路径走同一个闸门**，区别只在 SQL 从哪来。

决策 11 让 T3.5 多了一层前置校验。指标结构化之后，聚合函数是否在白名单内、字段是否存在、过滤值类型是否匹配，都能在拼接 SQL 之前查出来，不必等到解析成品 SQL 才发现问题。这层校验的报错质量直接决定用户看到的是"字段不存在"还是"SQL 语法错误"。

**验收基准**：准备 10 条左右的越界用例——`DROP`、多语句、未授权表、未授权字段、`INTO OUTFILE`、临时函数、注释绕过、笛卡尔积炸弹、超时查询、超量返回。全部被拒绝或被安全截断，且原因可追溯。这个用例集是 T3.6 / T3.7 的主要交付物之一，后续改动都要跑它。

## 7. M4 SQL 记忆

| 编号 | 任务 | 交付物 | 验收要点 |
|---|---|---|---|
| T4.1 | 问题规范化与结构化标签 | 归一文本 + 涉及的表、指标标签 | 同一问题的不同写法归一到同一形态 |
| T4.2 | BM25 索引 | SQLite FTS5 索引与查询 | 精确标识符命中优先于泛化词 |
| T4.3 | 向量索引 | 本地 embedding 模型 + `sqlite-vec` | 改写问法能召回语义相近的历史 SQL |
| T4.4 | RRF 融合与前置过滤 | 结构化过滤 + BM25 + 向量三路，RRF 融合排序 | 表不兼容的历史 SQL 不进入候选 |
| T4.5 | 反馈闭环 | 记录被召回的 SQL 是否被采用、是否执行成功 | 反馈可作为排序信号回灌 |
| T4.6 | 记忆写入与失效策略 | 成功回写、失败不入库、语义层版本隔离 | 语义层变更后旧记忆不误导生成 |

决策 3 的落地要点在 T4.4 的顺序：**结构化过滤在排序之前**。语义层已经知道哪些表和指标可以一起问，这层过滤比排序算法更能挡住错误召回。

## 11. 横切关注点

测试策略按风险分层，不追求平均覆盖：

- **安全用例集**：T3.6 / T3.7 的越界 SQL 用例，作为回归基线长期保留。这是风险最高的地方，测试密度应该最高。
- **状态机与错误分类**：纯逻辑，单测覆盖全部流转和分类分支。
- **存储层**：用临时库跑，验证事务与并发写。
- **语义层漂移**：T3.3 要有一条 CI 用例，故意改物理 schema 验证报警能触发。
- **EventLog 解析**：准备几份脱敏的真实日志作为固定样本，不靠手工构造。
- **端到端**：M5 之后每个里程碑补一条。

## 12. 风险

**语义层覆盖率是主路径的成败点**。决策 2 把常规问数交给语义层编译，如果语义层只覆盖少量问法，用户会被推给逃生舱，等于绕开了最安全的路径。缓解方式是把"语义层未命中率"当成一个显式指标，在 T3.9 的端到端里统计。

**混合检索引入外部依赖**。T4.3 需要本地 embedding 模型，这给镜像体积和启动时间加了负担。缓解方式是先做 T4.2 的 BM25 并把 T4.4 的融合接口留好，把向量做成可插拔的一路，缺了也不影响主流程。

**Spark 环境成本**。JDK、Python、Spark 三者互相牵制，M0 的 Docker 如果拖太久会阻塞一切。缓解方式是 T0.3 先保证 `local[*]` 和 `local-cluster` 可用，standalone 推到 T6.5。

**诊断规则的可信度**。阈值拍脑袋定，结论就不可信。缓解方式是 T6.2 先把指标打出来看，再在 T6.3 定阈值，并且每条规则都输出触发的具体数值。

**合成数据不反映真实分布**。诊断规则的阈值是在合成数据上调出来的，搬到真实数据上未必成立。缓解方式是把阈值做成可配置并标注"基于合成数据标定"，同时规则只输出结论和原始数值，重标定时不用改结构。

**模型 API 的输出会漂移**。DeepSeek 的模型会静默更新，JSON 合规率和生成习惯都可能变化。缓解方式是 pin 模型名、把每次调用的模型版本与 token 用量记进 Attempt，并且 Planner 的输出校验按硬失败处理，不做尽力解析。
